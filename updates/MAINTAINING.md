# 기능별 업데이트 관리 규칙

1. 기능 하나에 한 디렉터리와 고정 ID를 사용합니다. 사용자 설정·사진·운영 데이터·로컬 배포 기록을 패치에 넣지 않습니다.
2. 기준 커밋과 선행 기능을 고정합니다. 다른 변경을 모아 한 번에 덮어쓰는 패치는 만들지 않습니다.
3. `update.patch`, `manifest.json`, `README.md`, `CODEX.md`를 함께 갱신합니다. manifest에 변경 파일, 전후 해시, 패치 해시, 선행 기능과 검사 명령을 기록합니다.
4. 기준본에서 개별 적용, 선행 기능 적용, 다른 업데이트와 결합, 역방향 복구를 검증합니다. 기존 사용자의 모든 수정본에서 통과한다고 주장하지 않습니다.
5. `node --test test/updates/check-feature-update.node.mjs`와 각 기능 테스트를 실행합니다.
6. `python3 scripts/package-feature-updates.py --output /원하는/출력폴더`로 기능별 ZIP과 체크섬을 만듭니다.
7. GitHub Releases에 ZIP·SHA256SUMS.txt를 첨부하고 README의 다운로드 링크를 해당 태그와 일치시킵니다. 이미 배포한 버전의 파일을 조용히 교체하지 말고 버전을 올립니다.
8. 릴리스 게시 후 기능 목록·첨부파일·크기와 체크섬을 다시 조회해 확인합니다. 체크섬은 손상 확인용이며 별도 서명이 아닙니다.

이번 릴리스의 원본 실행 코드는 기준 커밋을 유지합니다. `main`에 문서/배포 묶음을 추가하는 것과 운영 사이트를 재배포하는 것은 별개입니다.

## GitHub에서 게시하기

`updates/release.json`의 태그·제목과 다운로드 링크·릴리스 설명을 갱신해 `main`에 올리면 `Publish feature updates` 작업이 검사·압축·임시 릴리스 업로드·다운로드 체크섬 확인 후 게시합니다. Actions 화면의 수동 실행도 지원합니다. 기존 태그가 있으면 덮어쓰지 않습니다. 포크 저장소에서는 원본 릴리스 게시 작업이 자동 실행되지 않습니다. Cloudflare 배포 권한이나 비밀값은 사용하지 않습니다.
